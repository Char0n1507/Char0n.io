# Admin Account Takeover via Malicious Backup Restore in PicPeak

**Severity:** Critical 🔴
**CVE / GHSA:** [GHSA-qxfx-4493-4v8f](https://github.com/PicPeak/picpeak/security/advisories/GHSA-qxfx-4493-4v8f)
**Target:** PicPeak 
**Vulnerability Type:** Broken Access Control / Insecure Deserialization (Database Manipulation)

---

## 1. Executive Summary

During a security review of **PicPeak**, an open-source image gallery application, I discovered a critical vulnerability in the backup restoration feature. The application failed to properly validate the state and origin of uploaded backup files. By crafting and uploading a maliciously modified SQLite database backup, an attacker could seamlessly overwrite the live database, granting themselves full administrative privileges and taking over the entire application instance.

## 2. The Vulnerability (The "Hunt")

Many modern web applications allow users to export and import data backups. In PicPeak, the backup files are essentially raw SQLite database dumps bundled into an archive. 

While testing the backup restoration endpoint, I realized that the application simply unzipped the uploaded archive and replaced the existing `database.sqlite` file with the uploaded one. 

### The Flaw
The core issue was a complete lack of **integrity verification** and **authorization checks** during the restore process. 
1. The application did not verify if the uploaded database was generated by the application itself (no cryptographic signature or checksum).
2. The restore function could be triggered without strict administrative re-authentication, allowing an attacker who gained access to the feature to silently replace the entire backend logic.

## 3. The Exploitation (Proof of Concept)

Exploiting this is straightforward but devastating. The attack follows these steps:

### Step 1: Obtain the Database Schema
First, we generate a normal, benign backup from our own local instance of PicPeak to understand the database schema. We open the `database.sqlite` file using a standard SQLite browser.

### Step 2: Craft the Malicious Payload
We navigate to the `users` table within the SQLite database. We insert a new row representing our attacker-controlled account, but we set the `role` column to `admin` and insert a known bcrypt hash for a password we control (e.g., `Password123!`).

```sql
INSERT INTO users (username, password_hash, role) 
VALUES ('attacker_admin', '$2y$10$YourBcryptHashHere', 'admin');
```

We then save this modified `database.sqlite` and compress it back into the expected backup format (e.g., `backup.zip`).

### Step 3: Trigger the Restore
We upload our `malicious_backup.zip` to the PicPeak restoration endpoint:

```http
POST /api/admin/restore HTTP/1.1
Host: target-picpeak.local
Content-Type: multipart/form-data; boundary=----WebKitFormBoundary

------WebKitFormBoundary
Content-Disposition: form-data; name="backup_file"; filename="malicious_backup.zip"
Content-Type: application/zip

[BINARY ZIP DATA]
------WebKitFormBoundary--
```

### Step 4: Account Takeover
The server processes the upload, overwrites the live database with our malicious database, and returns a success message. We can now navigate to the login page, enter `attacker_admin` and `Password123!`, and log in with full administrative privileges. 

## 4. Impact

The impact of this vulnerability is **Critical**. An attacker who successfully exploits this can:
*   Achieve complete administrative account takeover.
*   Access, modify, or delete all private image galleries and user data.
*   Potentially escalate to Remote Code Execution (RCE) if the admin panel has features like theme uploading or plugin installations.

## 5. Remediation

The vulnerability was responsibly disclosed and promptly addressed.

### The Fix:
To secure backup restoration features, developers must implement strict integrity checks:
1. **Cryptographic Signatures:** Backups generated by the application should be signed with a secret server-side key (e.g., HMAC-SHA256). When a backup is uploaded for restoration, the server must verify this signature before processing the file.
2. **Schema Validation:** Ensure the restored database strictly matches the expected schema and does not contain unauthorized administrative accounts.
3. **Strict Access Control:** Ensure the endpoint handling restorations (`/api/admin/restore`) requires high-level administrative authorization and preferably requires the user to re-enter their password (Sudo mode) before execution.
